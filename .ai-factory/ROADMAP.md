- [x] **Crossfade between breathing phases via ping-pong loop players** — currently `_switchToPhase` fades out then fades in on the same player, producing a silence gap at every phase transition. - [x] **Fix two crossfade bugs: missing first-cycle audio and residual silence gap** — background: `BreathSoundCoordinator` uses a ping-pong pair `_loopPlayerA` / `_loopPlayerB`; on each phase switch `_inactiveLoop` is seeked to the new phase index and faded in while `_activeLoop` fades out, then references are swapped. Both players have the same three-track playlist loaded via `setAudioSources` at `initialize()`. Bug (1): `_loadFuture` is assigned only from `_loopPlayerA.setAudioSources(...)`; `_loopPlayerB.setAudioSources(...)` is fired unawaited with no future stored. In `_switchToPhase`, `await _loadFuture` only guarantees player A is ready. On the very first phase switch `_inactiveLoop` is B — which may still be loading — so `seek` on B silently no-ops and the entire first breathing cycle is silent. On the second cycle the roles are swapped and A (guaranteed ready) is inactive, so it works. Fix: replace the two separate `setAudioSources` calls with a single `_loadFuture = Future.wait([_loopPlayerA.setAudioSources(sources, preload: true), _loopPlayerB.setAudioSources(sources, preload: true)])` in `initialize()`; `_switchToPhase` already awaits `_loadFuture` so no other change needed. Bug (2): a silence gap persists on every phase transition even when both players are ready — root cause is timing: step-5 fires at `remainingTicks == 1` and fades `_activeLoop` to 0.0 over `currentIntervalMs` (~1s); by the time the phase actually changes and `_switchToPhase` is called, `_activeLoop` is already silent; `_inactiveLoop` then needs `seek` + `play` (async, even on a preloaded player there is a brief pipeline flush on Android) before it produces sound — during this window both players are silent. Fix: delete step-5 from `_onStateChanged` entirely; instead, pass `fadeDuration` into `_switchToPhase` derived from `state.currentIntervalMs` at the call site in `_onStateChanged` step-4; inside `_switchToPhase`, after `play()` on the inactive player, fire both fades concurrently — `_fadePlayer(_inactiveLoop, 1.0, fadeDuration)` and `_fadePlayer(_activeLoop, 0.0, fadeDuration)` — so the outgoing sound is still audible while the incoming one ramps up, eliminating the gap. Transitions into rest/pause (no phase change, handled by step-3 in `_onStateChanged`) keep calling `_fadePlayer(_activeLoop!, 0.0, ...)` directly and are unaffected by this change. [10m 48s]

- [x] **Fix two crossfade bugs: hung `play()` on first cycle and late crossfade start** — background: `_switchToPhase` is an async method called fire-and-forget via `unawaited`. Two concurrent invocations can overlap on the same `_inactiveLoop` player. Bug (1): current code does `await inactive.play()`. When gen=N is awaiting `play()` on player B and gen=N+1 arrives (because gen=N never completed the swap, so `_inactiveLoop` is still B), gen=N+1 calls `seek()` on B while gen=N is still suspended inside `await play()`. ExoPlayer receives conflicting commands; gen=N's `play()` Future never resolves until the player is disposed (~36s later, confirmed by logs: `play() done gen=1 BAIL` appears at dispose time). This makes every odd-numbered gen produce no sound because the swap never happens and `_activeLoop` stays stale. Fix: replace `await inactive.play()` with `unawaited(inactive.play())` — do the swap and start both fades immediately after `seek()` returns, without waiting for playback to physically start; audio begins within milliseconds as the preloaded pipeline is already primed. Bug (2): even with the fix above, both fades start ~150–270ms after the phase change because `seek()` itself takes that long (pipeline flush on Android even with a preloaded playlist, confirmed by timestamps: phase logged at e.g. 19:12:33.838, fades fire at 19:12:34.112 = 274ms later). During those 274ms the active player is still at full volume with no fade started, so the crossfade begins noticeably late into the new phase. Fix: start `_fadePlayer(_activeLoop!, 0.0, fadeDuration)` immediately when `_switchToPhase` is entered — before the `await seek()` call — so the outgoing sound begins fading out at the exact moment the phase change is detected; after `seek()` + `unawaited(play())` complete, start `_fadePlayer(_inactiveLoop!, 1.0, fadeDuration)` for the incoming sound; the two fades now straddle the seek latency symmetrically. [10m 12s]

- [x] **Adaptive crossfade duration based on incoming phase length** — currently `fadeDuration` passed to `_switchToPhase` is always `currentIntervalMs` (~1000ms for clock tick), regardless of how long the next phase is. For a 2s phase a 1s crossfade consumes half the phase; for a 15s phase 1s is imperceptibly short. Fix: compute `fadeDuration` at the call sites in `_onStateChanged` (step-3 breath branch and step-4 phase-change branch) using a power curve that gives a good perceptual feel across the full range. The formula: `fadeDurationMs = (k * pow(nextPhaseMs, 0.65)).clamp(minFadeMs, maxFadeMs).toInt()` where `nextPhaseMs = state.currentPhaseTotalDuration * intervalMs` (total incoming phase duration in ms), `k = 3.83` (calibrated so a 4s phase → ~1000ms fade), `minFadeMs = 150`, `maxFadeMs = 1500`. Reference table: 1s phase → ~160ms, 2s → ~310ms, 3s → ~680ms, 4s → ~1000ms, 8s+ → 1500ms (capped). Expose the three constants as `static const` fields at the top of `BreathSoundCoordinator` (`_kFadeCoeff`, `_kMinFadeMs`, `_kMaxFadeMs`) so they can be tuned without searching through logic. `state.currentPhaseTotalDuration` and `state.currentIntervalMs` are already available at both call sites — no changes needed to `_switchToPhase` signature or `BreathSessionState`. [12m 56s]

- [ ] **Fix `GrpcAuthInterceptor.interceptStreaming` sending no auth header on first stream open** — `lib/Core/Grpc/GrpcAuthInterceptor.dart`: `interceptUnary` attaches the token via `CallOptions(providers: [_addAuthMetadata])`, which reads from `FlutterSecureStorage` lazily at call time and populates `_cachedToken` as a side-effect. `interceptStreaming` skips this and reads `_cachedToken` directly from a static field — if no unary call has been made yet (e.g. both `SyncGrpcListener` and `ModuleStateChannel` open their streams immediately after `GrpcConnectionManager.connect()` succeeds, before any unary request fires) `_cachedToken` is `null` and no `authorization` header is sent, causing the server to return `UNAUTHENTICATED` in a reconnect loop.
