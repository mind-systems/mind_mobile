# Biometric stream readiness gate (client) — buffer until server `ready`

**Date:** 2026-06-18
**Source:** conversation context — note 44 verified empirically

## Key Findings

- `BiometricStreamClient` (`lib/Biometrics/BiometricStreamClient.dart`) hits the same cold-start/reconnect race as the instruction tunnel: `_ensureSinkOpen()` opens the bidi stream and, immediately after, drains the replay ring into the fresh sink (`_encodeAndAdd(replay)`) — before the server's post-auth `request.subscribe()` runs, so the first batch can be dropped.
- The data-loss cost here is **low** (biometrics are a continuous high-rate stream; losing the first batch ≈ a fraction of a second), unlike the instruction tunnel's one-shot `rest`. This task is therefore lower priority and independently shippable from note 114.
- The fix mirrors note 114: gate all outbound batches (and the replay drain) on the server `ready` frame (new `BioStreamResponse.event.ready` arm from mind_api note 48), re-armed on every `_ensureSinkOpen`.

## Details

### Prerequisite

mind_api note 48 deployed (server emits `BioStreamReady`). The proto copy + `./scripts/gen_proto.sh` is done by note 114 (first consumer); this task reuses the regenerated `module_biometric_stream` stubs. If note 114 has not run, copy+regen here instead.

### The gate — `lib/Biometrics/BiometricStreamClient.dart`

- Add `bool _isReady = false;`.
- `_ensureSinkOpen()`: set `_isReady = false` when opening the new sink. Do **not** drain the replay ring at the end of `_ensureSinkOpen` anymore — defer the drain to the `ready` handler.
- Response listener: handle `BioStreamResponse_Event.ready` — set `_isReady = true`, then drain the replay ring (`final replay = _replayRing.toList(); _replayRing.clear(); if (replay.isNotEmpty) _encodeAndAdd(replay);`).
- `_encodeAndAdd(samples)`: when `_sink != null` but `!_isReady`, route samples to the replay ring (`_enqueueReplay`) instead of `_sink.add`. Only add to the sink once `_isReady`. This keeps the existing bounded drop-oldest semantics (max 75) as the pre-ready buffer — acceptable given the low cost.
- Fallback net: a `Timer` started on open (e.g. 5 s) that, if `!_isReady` when it fires, logs a warning and forces `_isReady = true` + drains — same rationale as note 114 (no deadlock against an un-upgraded server). Cancel on `ready` and on `_teardownSink`.

### Guards

- Logging only through `logPrint`.
- Keep the 2-second reopen cooldown and the replay-ring cap (75) unchanged — the gate adds a readiness condition, it does not replace the ring.
- Do NOT implement eager-open.
- Reuses the proto regenerated by note 114; no separate proto edit.

### Verify

Start a session with a biometric source active; force a reconnect mid-session and confirm the first post-reconnect batch is persisted (no gap at the reconnect boundary in `bio_session_samples` for the `moduleSessionId`).

## Open Questions

- Whether biometrics even warrants the gate is a judgment call (low loss cost). Kept as a separate, deferrable task so the decision is the user's via priority — not a design gap.
