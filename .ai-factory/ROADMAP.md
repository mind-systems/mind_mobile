- [x] **Fix two crossfade bugs: hung `play()` on first cycle and late crossfade start** — background: `_switchToPhase` is an async method called fire-and-forget via `unawaited`. Two concurrent invocations can overlap on the same `_inactiveLoop` player. Bug (1): current code does `await inactive.play()`. When gen=N is awaiting `play()` on player B and gen=N+1 arrives (because gen=N never completed the swap, so `_inactiveLoop` is still B), gen=N+1 calls `seek()` on B while gen=N is still suspended inside `await play()`. ExoPlayer receives conflicting commands; gen=N's `play()` Future never resolves until the player is disposed (~36s later, confirmed by logs: `play() done gen=1 BAIL` appears at dispose time). This makes every odd-numbered gen produce no sound because the swap never happens and `_activeLoop` stays stale. Fix: replace `await inactive.play()` with `unawaited(inactive.play())` — do the swap and start both fades immediately after `seek()` returns, without waiting for playback to physically start; audio begins within milliseconds as the preloaded pipeline is already primed. Bug (2): even with the fix above, both fades start ~150–270ms after the phase change because `seek()` itself takes that long (pipeline flush on Android even with a preloaded playlist, confirmed by timestamps: phase logged at e.g. 19:12:33.838, fades fire at 19:12:34.112 = 274ms later). During those 274ms the active player is still at full volume with no fade started, so the crossfade begins noticeably late into the new phase. Fix: start `_fadePlayer(_activeLoop!, 0.0, fadeDuration)` immediately when `_switchToPhase` is entered — before the `await seek()` call — so the outgoing sound begins fading out at the exact moment the phase change is detected; after `seek()` + `unawaited(play())` complete, start `_fadePlayer(_inactiveLoop!, 1.0, fadeDuration)` for the incoming sound; the two fades now straddle the seek latency symmetrically. - [x] **Adaptive crossfade duration based on incoming phase length** — currently `fadeDuration` passed to `_switchToPhase` is always `currentIntervalMs` (~1000ms for clock tick), regardless of how long the next phase is. Fix: compute `fadeDuration` at the call sites in `_onStateChanged` (step-3 breath branch and step-4 phase-change branch) using a power curve that gives a good perceptual feel across the full range. The formula: `fadeDurationMs = (k * pow(nextPhaseMs, 0.65)).clamp(minFadeMs, maxFadeMs).toInt()` where `nextPhaseMs = state.currentPhaseTotalDuration * intervalMs` (total incoming phase duration in ms), `k = 3.83` (calibrated so a 4s phase → ~1000ms fade), `minFadeMs = 150`, `maxFadeMs = 1500`. Reference table: 1s phase → ~160ms, 2s → ~310ms, 3s → ~680ms, 4s → ~1000ms, 8s+ → 1500ms (capped). Expose the three constants as `static const` fields at the top of `BreathSoundCoordinator` (`_kFadeCoeff`, `_kMinFadeMs`, `_kMaxFadeMs`) so they can be tuned without searching through logic. `state.currentPhaseTotalDuration` and `state.currentIntervalMs` are already available at both call sites — no changes needed to `_switchToPhase` signature or `BreathSessionState`.
