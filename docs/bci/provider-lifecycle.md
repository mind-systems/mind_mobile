# Жизненный цикл BCI-провайдера

`NeiryBciProvider` управляет одним физическим подключением к устройству. Внутри него несколько дорогостоящих объектов — локатор устройств, дескриптор устройства, набор классификаторов — каждый из которых держит нативные ресурсы и требует строго определённого порядка завершения.

## Проблема конкурентности

Локатор, устройство и классификаторы разделяются между несколькими путями: сканирование, подключение, отключение, внезапный обрыв соединения. Каждый из этих путей модифицирует одни и те же объекты. Если два пути запускаются одновременно — например, автоматическое переподключение накладывается на явное отключение — без явной координации порядок операций непредсказуем.

## Очередь как инвариант

Решение: все операции над нативными ресурсами проходят через одну последовательную очередь. Очередь гарантирует, что в любой момент времени выполняется ровно одна операция. Следующая начинается только после того, как предыдущая полностью завершена — включая все ожидания SDK.

Благодаря этому исчезают три класса ошибок:
- **Зависание при переподключении** — попытка запустить сканирование, пока старый локатор ещё не освобождён.
- **Утечка** — классификатор или устройство создаются в новом подключении, пока завершение предыдущего ещё в процессе.
- **Гонка teardown** — два пути одновременно вызывают `dispose()` на одном объекте.

## Порядок завершения

Правило SDK: остановить стриминг, отменить подписки, освободить классификаторы, отключить устройство, освободить устройство, освободить локатор. Нарушение порядка приводит к падению в нативном коде. Очередь гарантирует, что этот порядок соблюдается независимо от того, какой путь инициировал завершение.

## Терминальное состояние

Когда приложение освобождает провайдер (`dispose`), очередь закрывается. Операции, которые пришли после закрытия, тихо игнорируются. Создание новых нативных ресурсов после закрытия не происходит.
