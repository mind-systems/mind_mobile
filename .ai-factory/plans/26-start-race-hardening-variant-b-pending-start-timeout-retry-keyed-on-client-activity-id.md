# Plan: Start-race hardening (variant B): pending-start + timeout + retry keyed on `client_activity_id`

## Context
Make a tapped-into-void practice survive a disconnect between `start` and its confirming ACTIVE frame: track a per-`activity_type` pending start, wait for a confirming ACTIVE/RESUMED frame, and on a 5s timeout re-send `start` with the **same** `client_activity_id` (dup-safe, retry-only-while-unconfirmed), adopting an already-live child instead of duplicating, and deferring the adopt-vs-new decision through the reconnect settling window.

## Grounding (re-pinned against the post-refactor tree)

- **Command level, not the FSM.** All pending/timeout/retry state stays command-level in `lib/Core/Grpc/ModuleStateChannel.dart` — note 25 §Guards explicitly keeps pending-start out of `ConnectionLifecycle`. The FSM is only *read* (to tell a first-connect open from a reconnect open).
- **The executable spec is already written.** `test/Core/Grpc/start_race_contract_test.dart` + `test/Core/Grpc/Support/reconnect_concurrency_harness.dart` encode INV-8…INV-12 / SC-1,2,3,7 as RED scenarios. Every assertion is on the **wire** (`sentRequests`), never on private pending fields. Do not weaken or rename these tests to pass; make production satisfy them.
- **Current anchors in `ModuleStateChannel.dart`:** single-bool guard `_isPendingStart` (`:44`), the shared start guard `if (currentState.status == ModuleStateStatus.active || _isPendingStart) return;` (`:333`), pending cleared on RESUMED (`:232-233`) and ACTIVE (`:242-243`), `_resetWholeTree()` clears the bool (`:426-431`), reconcile-by-arrival window armed on every `_openSessionStream` (`:145-157`, `_arrivedChildIds` `:56`), FSM entry/transition (`_lifecycle` `:68`, `_transition` `:73`, connected handler `:108-122`), `takeOverHere()` (`:324-328`), `childOfType` getter (`:38`), `dispose()` (`:441-450`).
- **Pinned constants (note 19 §Pinned constants):** confirm timeout **5s** per attempt; **max 2 retries** (3 attempts total); settling window **3s** (already the `_reconcileTimer` duration `:149`).
- **Adapters already mint & keep the token:** `BreathModuleStateChannel` (`:94-100`, `_clientActivityId` `:24`) and `MeditationModuleStateChannel` (`:54-60`, `_clientActivityId` `:17`) generate the UUID and pass it into `channel.start(...)`. Retry reuse lives inside `ModuleStateChannel` (it receives the token per start), so adapters need **no** token-reuse change.

## Design: the two send helpers (referenced across tasks)

To keep the initial send, the retry, and the settling-window release consistent, all three go through one pair of private helpers on `ModuleStateChannel`:

- **`_beginStart(_PendingStart p)`** — registers `p` in `_pendingStarts[p.type]` (replacing any prior entry, cancelling its timer), then calls `_sendStart(p)`. This is the single entry that makes a start *pending* (owns the confirm-timeout + retry lifecycle). Used by `start()`'s initial send **and** by Task 4's deferred-start release, so a released deferred start gets the same 5s timeout + bounded retry as any other start (closes the INV-8 gap the reviewer flagged).
- **`_sendStart(_PendingStart p)`** — increments `p.attempts`, builds the `ActivityStartCmd` from `p`'s stored fields (same token every time), sends it, and arms `p.timer` for the 5s confirm timeout. Called by `_beginStart` (first send) and by `_onConfirmTimeout` (retry). Does **not** itself register the pending — the pending already exists by the time a retry fires.

### Phase 3: Reconnect settling-window deferral & carried-pending resolution

- [x] **Task 4: Defer adopt-vs-new during the reconnect settling window; resolve at window close** (depends on Task 2)
  Files: `lib/Core/Grpc/ModuleStateChannel.dart`
  The settling deferral must apply **only after a reconnect**, never on the first connect (first-connect starts must reach the wire immediately — INV-8/SC-2).   In `start()`, insert the settling check **after** the adopt-existing step and before the send (adopt still wins — an already-live same-type child is adopted immediately even during settling; Task 1 pinned adopt as step 1): when `_settlingActive` is true and no same-type child exists, do **not** send — stash a `_PendingStart` in `final Map<ActivityType, _PendingStart> _deferredStarts` and return.
  Extend the reconcile timer callback (`:149-157`), after the note-20 child-eviction sweep, to resolve both maps: for each **deferred** start, adopt (discard) if `_registry.childOfType(type) != null`, else release it via `_beginStart` (so it becomes a first-class pending with its own 5s timeout + bounded retry — not a fire-once send); for each **carried pending** start whose `type` did not re-arrive (not in `_arrivedChildIds` / registry), re-send with the same token via `_sendStart`.
  **Double-fire guard (review issue 4):** while `_settlingActive`, the settling window owns carried-pending resolution exclusively — cancel each carried `_PendingStart`'s own confirm timer when the window arms (on reconnect open), so a re-armed offline timer cannot also fire inside the 3s window. The window-close callback re-arms the confirm timeout (via `_sendStart`) for any pending it re-sends. (Even if both fired, the same `client_activity_id` is dedup-safe within the ~10s server window — but the cancel keeps the 3-attempt budget honest and avoids doubled wire traffic.)
  Clear `_deferredStarts`/`_settlingActive` on `_resetWholeTree()` and `dispose()`. Do not touch the first-connect path — `_settlingActive` stays false there, so the 5s retry timing (Task 2) is untouched.
  Greens INV-11 (deferred-then-adopted and deferred-then-released) and SC-3; must not regress INV-8/SC-2/INV-12 first-connect timing.
