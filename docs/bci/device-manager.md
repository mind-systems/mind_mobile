# BCI-устройство

Слой `lib/Bci/` отвечает за работу с нейроинтерфейсом как с физическим устройством: поиск, подключение, проверка качества сигнала, калибровка и реестр известных устройств пользователя. Никто выше этого слоя не знает о конкретном вендоре — для остального кода устройство выглядит как набор стримов состояния и биосигналов.

## Состояния подключения

Менеджер удерживает явную стейт-машину, реализованную как sealed-иерархия классов. Устройство проходит через неё от появления в эфире до готовности отдавать классифицированные данные:

```
BciIdle → BciScanning → BciConnecting → BciImpedance → BciCalibrating → BciReady
                │
                └─▶ BciPermissionDenied
```

`BciIdle` — нет активного подключения и активного сканирования. `BciScanning` — идёт BLE-поиск. `BciConnecting`, `BciImpedance`, `BciCalibrating`, `BciReady` — устройство-связанные фазы (наследники `BciActive`), каждая несёт `serial` целевого устройства, поэтому состояния вида «подключение без серийника» неrepresentable.

`BciImpedance` — устройство подключено по BLE, идёт проверка прижима электродов; пользователь физически сидит, ждёт зелёных индикаторов. `BciCalibrating` несёт `totalStages` — 4 для полного прогона, 1 для быстрой повторной калибровки. `BciReady` достигается только после успешной калибровки; до этого классификаторы EEG-производных метрик не считаются надёжными.

Переход в `BciPermissionDenied` — это не ошибка устройства, а отказ системы. Менеджер выставляет его, чтобы UI мог объяснить пользователю, что без разрешения сканирование физически невозможно, и предложил открыть системные настройки.

## Разрешения Bluetooth

Запрос разрешений происходит ровно в момент попытки сканирования — не на старте приложения. На Android запрашиваются `BLUETOOTH_SCAN` + `BLUETOOTH_CONNECT` (плюс location на API < 31). На iOS запрос выполняет системный BLE-стек при первом обращении.

Различаются два типа отказа: «временный отказ» (на Android — пользователь нажал Deny один раз, система ещё разрешит запросить снова) и «постоянный» (Don't Ask Again / iOS-настройки). В первом случае сканирование тихо завершается пустым результатом, во втором — поднимается типизированное исключение, и менеджер переходит в `BciPermissionDenied`. Открытие настроек инициирует UI, не домен.

## Известные устройства и авто-подключение

Сервер хранит реестр устройств, с которыми пользователь раньше успешно соединялся. После каждого успешного коннекта мобильник идемпотентно регистрирует серийник, после холодного старта подтягивает актуальный список и кладёт его в локальный кэш (SharedPreferences) — чтобы при следующем запуске работало офлайн.

Авто-подключение — это правило: «если во время сканирования среди обнаруженных устройств нашёлся серийник из кэша, остановить скан и подключиться к нему». Кэш читается синхронно в момент старта сканирования — если кэш пуст, авто-подключение не срабатывает.

## Авто-переподключение после обрыва

Когда подключённое устройство пропадает само по себе (вышло из зоны, разрядилось), менеджер реагирует переходом в `BciIdle` и сразу запускает повторный поиск ровно того же серийника. Это не повторяется бесконечно — если пользователь нажал «Отключить» вручную, ставится флаг подавления, и авто-переподключение не активируется до следующего ручного скана.

Логика отличает «пользователь хочет отключиться» от «связь временно потерялась» именно по источнику события: ручной disconnect выставляет флаг, неожиданное падение по BLE — нет.

## Калибровка

Калибровка инициируется явно, из состояния `BciImpedance`. Прогресс приходит этапами (stage-progress) — UI рисует индикатор. На успешное завершение с валидным результатом (`isValid == true`) менеджер переходит в `BciReady`. Невалидный результат (`isValid == false`) и технический сбой калибрации не являются фатальными — менеджер возвращается в `BciImpedance`, и пользователь может повторить попытку без переподключения.

Только валидные результаты сохраняются: при `isValid == true` менеджер записывает `NfbCalibrationData` в репозиторий (локально и fire-and-forget на сервер). Невалидные результаты не записываются.

Результат калибровки — это персональные пороги классификатора, привязанные к конкретному серийнику. При каждом новом подключении калибровка выполняется пользователем вручную заново. Сырые данные калибровки никогда не покидают адаптер устройства — наружу выставляются только типизированные доменные события.

## Поток типизированных событий

Менеджер сам по себе не предназначен для прямой подписки из UI. Над ним стоит нотификатор, который сводит все стримы (состояние, обнаруженные устройства, качество сигнала, батарея, события калибровки, биосэмплы) в единый поток типизированных событий с одной seed-emission. Это контракт для presentation-слоя — он подписывается на один стрим и pattern-match-ит по варианту события.

## Границы

- `lib/Bci/` — пуристый Dart-домен, ни одного импорта Flutter/Riverpod. Единственный файл, импортирующий вендор-SDK (`neiry_kit`), — конкретный адаптер устройства.
- Биометрические стримы (HR, RR, EEG-полосы, эмоции) технически проходят через адаптер, но они **не часть** контракта устройства — устройство класса BCI просто реализует соответствующие capability-интерфейсы. Подробности — в [docs/biometrics/capability-sources.md](../biometrics/capability-sources.md).
