## Phase 57 — Pluggable tick cadence sources: RR primary + HR-derived fallback

The breath "heart" tick path couples smoothing (`SmoothedRrSource`), staleness (`HeartRateTickService`'s 10 s `_coastGraceWindow`) and the metronome into one place, and feeds only RR. In `neiry_kit` RR is computed by us on raw PPG while HR (BPM) is computed by the SDK on a separate tract — so RR can fail (observed: 45 s of solid `isArtifact=true` + a mislabeled `430 ms` "2× fast" spike) while HR keeps streaming. Goal: each cadence source fully encapsulates its own smoothing + "usable now?" status; a selector keeps all warm and auto-picks the highest-priority usable one, so a future HR-only sensor rides the same code. `ActiveRrSource` is explicitly out of scope (no liveness "fix").

- [x] **Re-decompose the cadence path into `ITickCadenceSource` + selector (behavior-preserving, RR only)** — Today smoothing, the 10 s grace, and the metronome are entangled across `SmoothedRrSource` + `HeartRateTickService`. Introduce `ITickCadenceSource` (`smoothedPeriodMs` stream, `isUsable`, `usableChanges`) in `lib/BreathModule/TickCadence/`; `RrTickCadenceSource(SmoothedRrSource)` absorbs the **entire** `_effectiveActive`/`_droppedReplay`/`_armGrace`/`_onGraceExpired` + 10 s `_coastGraceWindow` machinery from `HeartRateTickService` (single home of RR staleness); `TickCadenceSelector(List)` keeps all sources warm and re-exposes the first usable by priority (pass-through for one source). Gut `HeartRateTickService` into a dumb metronome consuming `selector.smoothedPeriodMs` (keep self-rescheduling timer + 250–3000 ms clamp; `hasActiveSource`/`hasActiveSourceStream` delegate to the selector; drop its grace). Rewire `BreathModule.dart:33-34`; `SwitchableTickService` and `ActiveRrSource`/`SmoothedRrSource` singletons (`App.dart:225-226`) untouched. One RR source → byte-equivalent behavior. Spec: `.ai-factory/notes/01-tick-cadence-source-contract.md`. [40m 50s]

Add generic `HeartRateTickCadenceSource(IHeartRateSource)` in `lib/BreathModule/TickCadence/`: on each `CardioData`, valid when `metricsAvailable && !hasArtifacts && heartRate > 0` → emit `(60000/heartRate).round()` as the period + own staleness window (~5–10 s); no extra SMA initially (BPM is already averaged — stacking one lags; smoothing kept an internal swappable detail, measured later). ## Phase 58 —  Breath lifecycle state machine — extract status/lifecycle from the tick FSM (TDD, Option A)

The breath module has a mature **tick** FSM (`BreathSessionStateMachine` progression) but no real **lifecycle** FSM. `BreathSessionStatus {pause,breath,rest,complete}` (`BreathSessionState.dart:5`) is a Cartesian smear of (lifecycle × phase-kind): `pause` means BOTH "not started" AND "manually paused" — discriminated only by the out-of-band `_hasStarted` (`BreathSessionStateMachine.dart:83`) — and breath/rest is encoded twice (in `status` and in `phase`). "Is the activity live" is reconstructed **three times** — `_hasStarted` (SM), `_started/_ended` (`BreathModuleStateChannel`), `ModuleState{idle,active}` (server) — so keep-alive has no clean local/offline signal. Plan: derive a clean local `isLive`, migrate consumers onto it (fixing the offline keep-alive gap), then surgically extract an owned lifecycle FSM — all under a characterization golden master at the **activity boundary**, with the **output schema** (`BreathSessionState` fields) as the versioned contract. The server adapter (`BreathModuleStateChannel`) is **not** re-architected — it stays server-gated and merely stops parsing `status` meanings, receiving an explicit `stop|pause|play`. Phases unnumbered (fluid). Supersedes Phase 56 (note 162) — its audio fix folds into the consumer-migration task below.
