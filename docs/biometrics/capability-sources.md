# Источники биометрических способностей

Слой `lib/Biometrics/` описывает биосигналы независимо от конкретного железа. Любой провайдер биоданных — BCI-гарнитура, часы, кольцо, медицинский датчик — выражает свои возможности через набор небольших capability-интерфейсов. Это разделяет «класс устройства» (которое умеет сканироваться, подключаться, калиброваться) и «способности» (что именно оно отдаёт наружу).

## Capability-миксины

Каждая способность — отдельный интерфейс с единственным стримом:

- **Heart Rate** — мгновенные значения пульса с флагами доступности и артефактов.
- **RR-интервалы** — длительность каждого удара (peak-to-peak в PPG). Это сырьё, из которого ретроспективно восстанавливается любая HRV-метрика серверным алгоритмом, единым для всех источников. Готовые фирменные индексы (стресс от часов, body battery и т.п.) не сравнимы между вендорами и сознательно не передаются.
- **EEG-полосы** — амплитуды δ / θ / α / SMR / β из NFB-классификатора.
- **Эмоции** — выходы высокоуровневого классификатора (внимание, расслабление, когнитивная нагрузка, контроль).
- **Движение** — пары акселерометра и гироскопа per-sample (тройки x/y/z). Источник несёт сырьё в единицах устройства; нормализация и сведение движения с разных частей тела (голова со шлема, запястье с часов) — задача серверной аналитики. Для медитации это базовый сигнал «насколько неподвижен пользователь»; per-sample timestamp от SDK сохраняет реальную инерциальную шкалу внутри батча.

Источник свободно реализует любое подмножество. Например, часы дают HR + движение запястья; гарнитура — HR + RR + EEG + эмоции + движение головы; кольцо — RR. Внутри домена это просто dart-интерфейсы, реализуемые конкретными адаптерами (`NeiryBciProvider` — единственный сегодня; будущие реализации добавляются без правок остальных слоёв).

## Тегирование источника

Кардио, RR и motion-сэмплы несут идентификатор источника из единого `SensorSource` enum (`neiry`, `garmin`, `polar`, `appleHealth`). Это не косметика — это позволяет:

- Параллельно собирать одну способность с нескольких устройств одновременно (например, пульс с гарнитуры + часов, движение с головы + запястья) и сравнивать или сводить на сервере.
- Принимать решение об артефактах с учётом источника: один и тот же spike может быть нормой для PPG и аномалией для ECG; движение головы и запястья имеют разные базовые амплитуды.
- Не терять информацию через client-side дедупликацию: оба сэмпла уходят на сервер с тегами, аналитика сама выбирает политику.

Для motion-сэмплов «локация на теле» сегодня выводится сервером из тега источника (`neiry` → голова, будущий `garmin` → запястье). Явное поле `bodyLocation` в envelope не добавляется до тех пор, пока один вендор не начнёт совмещать данные с разных мест (Apple Health и подобные агрегаторы) — добавится в `data`-карту без слома proto-контракта.

EEG и эмоции сегодня приходят только с BCI, поэтому источник там подразумевается. Когда появится второй EEG-провайдер, тегирование расширится симметрично — без слома envelope.

## Параллельные источники

Маршрутизатор биопотоков принимает произвольное число источников на одну способность. При регистрации второго HR-источника он не падает и не дедуплицирует — оба потока сливаются, каждый сэмпл уходит наружу с тегом. Это сознательное решение в пользу полноты данных: client-side выбор «лучшего» источника был бы безвозвратной потерей.

## Контракт жизненного цикла

Все источники регистрируются на этапе инициализации приложения, до первого подписчика на сводный поток. Регистрация после старта подписки не вызовет ошибку, но новые сэмплы из позднего источника не дойдут до уже подписанного потребителя — это намеренно упрощённая модель, рассчитанная на статическую конфигурацию провайдеров.

См. [docs/biometrics/stream-pipeline.md](stream-pipeline.md) — как сэмплы из source-источников превращаются в трафик на сервер.
