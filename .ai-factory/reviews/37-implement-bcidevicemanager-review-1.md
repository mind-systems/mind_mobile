## Findings

### 1. Unexpected-disconnect listener does not exclude `connecting` — diverges from spec, can re-trigger reconnect while a connect is in flight (MEDIUM)
`_subscribeProviderStreams` (`BciDeviceManager.dart:40-50`):

```dart
if (state == BciConnectionState.disconnected &&
    _state != BciConnectionState.disconnected &&
    _state != BciConnectionState.scanning) {
  ...
  if (!_suppressAutoReconnect && _connectedSerial != null) {
    unawaited(_attemptReconnect());
  }
}
```

The spec (§ "Unexpected disconnect handler") describes the trigger as *"provider emits disconnected while state >= impedance"* — i.e. only from `impedance / calibrating / ready`. The implemented guard also fires from `connecting`.

For the *first* connect this is harmless: `_connectedSerial` is null during the initial `connecting` window (it is assigned only after `await _provider.connect(serial)` succeeds), so the inner `_connectedSerial != null` guard skips reconnect.

For a *re-connect*, the sequence below cascades:

1. User connects → `_state = impedance`, `_connectedSerial = "ABC"`.
2. Provider emits `disconnected`. Listener fires, transitions to `disconnected`, schedules `_attemptReconnect()`.
3. `_attemptReconnect()` sets `_state = scanning`, opens a new scan.
4. Scan finds "ABC", calls `connectDevice("ABC")` → `_state = connecting`. `_provider.connect()` is awaited.
5. Provider emits `disconnected` again (e.g. flapping BLE) before the connect resolves. Listener guard: `state == disconnected` ✓, `_state != disconnected` ✓ (it's `connecting`), `_state != scanning` ✓. → triggers `_attemptReconnect()` a **second time** while `connectDevice` is still awaiting.
6. The new `_attemptReconnect()` runs `_setState(scanning)` (overrides `connecting`), then `await _scanSub?.cancel()` — but `_scanSub` here is the new reconnect-scan subscription opened in step 3; cancelling it does **not** abort the in-flight `await _provider.connect()`. A *third* scan is opened.

End state: the previous `connectDevice` eventually resolves and calls `_setState(impedance)`, but `_state` is `scanning` (per step 6), and there are now two interleaved scan handlers running on different `_scanSub` instances. Stream emissions go to whichever was assigned last; the older scan handler is detached but still runs to completion of any in-flight `await connectDevice(...)`.

**Fix:** add `_state != BciConnectionState.connecting` to the guard so a flap during a reconnect attempt is treated as the in-flight `connectDevice` problem (the existing `try/catch` in `connectDevice` will transition to `disconnected` when `provider.connect` throws / completes against a torn-down device).

### 2. Possible "Bad state: Cannot add new events after calling close" if `dispose()` races a scan handler (MEDIUM)
`dispose()` (`BciDeviceManager.dart:86-92`) cancels subscriptions then closes controllers:

```dart
await _connectionStateSub?.cancel();
await _calibrationSub?.cancel();
await _scanSub?.cancel();
await _stateController.close();
await _discoveredDevicesController.close();
```

The scan handler in `startScan()` / `_attemptReconnect()` is an `async` callback that awaits `connectDevice` (which itself awaits `_provider.connect`). Per Dart semantics, `StreamSubscription.cancel()` for a single-subscription stream waits for the *currently-delivering* synchronous portion of the handler, but it does **not** await the handler's outstanding async continuation. If `dispose()` is called while a scan handler is parked on `await _provider.connect(serial)`:

1. `await _scanSub?.cancel()` resolves (no more deliveries will be made).
2. `await _stateController.close()` completes.
3. The provider connect eventually resolves; `connectDevice` continues, calls `_setState(BciConnectionState.impedance)`, which calls `_stateController.add(...)` on a **closed** controller → `StateError`.

`unawaited(_repository.registerDevice(serial))` after that is also fired against a half-disposed manager.

This is a real but narrow race — it requires the user (or upstream caller) to dispose the manager while a connect attempt is mid-flight. The risk grows once `BciNotifier`/the UI screen is wired (close screen → unmount). Worth fixing now:

- Track a `bool _disposed`; in `_setState`, early-return when `_disposed || !_stateController.hasListener && _stateController.isClosed`. The simplest robust shape is:
  ```dart
  void _setState(BciConnectionState next) {
    if (_disposed || next == _state) return;
    _state = next;
    if (!_stateController.isClosed) _stateController.add(next);
  }
  ```
  and set `_disposed = true` at the top of `dispose()`. Apply analogous protection to `_discoveredDevicesController.add(...)` in the scan handlers.

### 3. `startCalibration()` has no state precondition — can leave the manager in `impedance` while disconnected (LOW)
`startCalibration()` (`BciDeviceManager.dart:137-147`) unconditionally transitions to `calibrating`, then calls `_provider.startCalibration()`. The catch block transitions back to `impedance` on failure.

If invoked while `_state == disconnected` (no device connected), the failure path leaves the manager in `impedance` with `_connectedSerial == null`. UI consumers that key off `state == impedance` would then render impedance UI for a device that isn't there.

The plan's Task 4 note marks the parallel issue for `connectDevice` as "informational". This one is symmetrical — flag for the upcoming `BciNotifier` / UI milestone or add a precondition `if (_state != BciConnectionState.impedance) return;` at the top of the method.

### 4. `disconnect()` does not cancel an in-progress scan (LOW)
`disconnect()` (`BciDeviceManager.dart:149-154`) tears down the provider connection and resets state, but if a scan is in progress (`_scanSub` is non-null), the handler keeps firing — it will overwrite `_discoveredDevices` and emit on `_discoveredDevicesController`. The `_state == scanning` guard in the handler prevents stray `connectDevice` calls, so this is not a correctness bug, but the leftover scan keeps Bluetooth active until it finishes (5 s in `NeiryBciProvider`) or `dispose()` is called.

Consider `await _scanSub?.cancel(); _scanSub = null;` at the start of `disconnect()`.

### 5. Late scan emissions after auto-connect keep mutating `_discoveredDevices` (INFORMATIONAL)
`NeiryBciProvider.scan()` runs for `searchTime: 5` seconds and emits multiple snapshots. After the scan handler auto-connects and the manager transitions past `scanning`, subsequent emissions still execute the lines before the guard:

```dart
_discoveredDevices = discovered;
_discoveredDevicesController.add(discovered);
if (cachedSerials.isEmpty) return;
final autoConnect = discovered.firstWhereOrNull(...);
if (autoConnect != null && _state == BciConnectionState.scanning) { ... }
```

The state guard correctly suppresses the auto-connect, but `_discoveredDevices` and the controller continue to update during connecting/impedance. UI lists driven by this stream will flicker. Cancel `_scanSub` once auto-connect is initiated, or move the `_state == scanning` check above the controller emission. Not blocking — matches the spec's stream behaviour — but worth a comment.

### 6. `_suppressAutoReconnect` is sticky after a manual disconnect that is not followed by `startScan()` (INFORMATIONAL)
Per spec, only `startScan()` clears the flag. So the sequence `startScan → connect → disconnect → connectDevice` (skipping a re-scan) leaves the flag at `true`, and an unexpected drop afterwards will not auto-reconnect. This is intentional per the spec, but the public API exposes `connectDevice` without scan, so a future caller could be surprised. Document the constraint in the public API doc or reset the flag inside `connectDevice` success path. Flagged for awareness; not a bug.

## Positive notes

- `_setState` is the single mutation funnel and short-circuits on duplicates — duplicate `_setState(disconnected)` calls during the disconnect race (provider event + manual reset) are silently coalesced.
- Subscription handles (`_connectionStateSub`, `_calibrationSub`, `_scanSub`) are assigned at construction so `dispose()` can cancel them — addresses plan-review item #3 correctly.
- `connectDevice` and `startCalibration` both wrap provider calls in try/catch and route failures to sensible recovery states.
- `onError` is wired on both scan subscriptions (per plan-review item #6), preventing zone-uncaught errors on Bluetooth-permission revocation.
- `package:collection` is added to `pubspec.yaml` as a direct dependency, satisfying `depend_on_referenced_packages` (plan-review item #1).
- `dispose()` correctly **does not** call `_provider.dispose()` — provider lifecycle ownership belongs to `App.initialize` per the next milestone.
