# Поток биоданных на сервер

Биометрический pipeline собирает сэмплы со всех зарегистрированных источников, пакует их в общий envelope, батчит и отправляет на сервер по двунаправленному gRPC-стриму — но только пока пользователь действительно работает в активной module-сессии. Это пассивная фоновая инфраструктура: UI про неё не знает, кода в presentation-слое нет.

## Слои

```
Источники (capability-mixins) ─▶ Router ─▶ Batcher ─▶ Client ─▶ gRPC
                                                         ▲
                                                         │
                                          ModuleStateChannel.events
```

- **Router** сливает потоки всех зарегистрированных источников в единый поток типизированных сэмплов. Каждый исходный объект (CardioData, RrInterval, NFB-полосы, эмоции) переводится в один общий envelope с типом сэмпла и payload-картой.
- **Batcher** копит сэмплы и сбрасывает их пачкой — по достижению размера или по короткому таймауту. Это снижает число RPC-вызовов без заметной задержки.
- **Client** владеет gRPC-стримом, держит идентификатор текущей module-сессии и решает, что с пачкой делать прямо сейчас.

## Гейтинг по module-сессии

Pipeline крутится всё время, пока приложение работает, но реально шлёт сэмплы только в окне `start → end` активной сессии. Источник истины — `ModuleStateChannel` (тот же канал, который рассылает lifecycle-команды в [docs/realtime/live-session-tracking.md](../realtime/live-session-tracking.md)).

Клиент подписывается на его события и держит две переменные: текущий `moduleSessionId` и флаг паузы. Без активной сессии или на паузе пачка молча отбрасывается. Это симметрично логике инструкционного стрима: сервер всё равно блокирует входящие сэмплы во время паузы, и буферизовать их на клиенте не имеет смысла — пользователь в эти моменты делает что-то неопределённое, и аналитический вес у таких данных низкий.

## Schema сэмпла

Каждый сэмпл, уходящий на сервер, — это общий envelope с тремя обязательными полями (идентификатор сессии, временна́я метка, тип сэмпла) и payload-картой, чья форма зависит от типа. Сами схемы payload-карт владеет мобильник — на сервере они приходят в виде generic-структуры (`google.protobuf.Struct`), без проверки формы proto-схемой. Это позволяет добавлять новые типы сэмплов без правок контракта.

Временна́я метка для RR-интервалов берётся от SDK (это физиологический момент удара). То же для motion-сэмплов — нативный MEMS-слой стампит каждый сэмпл индивидуально, и сохранять эти метки критично, потому что батч в `DateTime.now()` склеил бы всю инерциальную шкалу внутри пачки в одну точку. Для остальных типов используется `DateTime.now()` в момент эмиссии — соответствующие SDK-стримы не несут собственного timestamp.

## Replay при обрыве gRPC

Когда отправка валится из-за обрыва соединения, сэмплы укладываются в небольшой ограниченный кольцевой буфер (drop-oldest). После восстановления стрима буфер опустошается перед приёмом новых сэмплов. Это страховка от потерь на коротких лагах сети — она не предназначена для длительных оффлайн-сценариев и сознательно ограничена по размеру.

Замечание: replay-буфер обслуживает обрыв соединения, не паузу. Сэмплы, пришедшие во время паузы, теряются безвозвратно — это политика, не баг.

## Корреляция с инструкционным потоком

Биометрический и инструкционный потоки идут разными gRPC-сервисами, но привязываются к одному `moduleSessionId`. Аналитика на сервере делает time-join по этому ключу: «в момент T+6000ms инструкция была exhale 6s — что показывал биосигнал в это окно?». Подробности схемы корреляции — в [docs/realtime/live-session-tracking.md](../realtime/live-session-tracking.md).

## Жизненный цикл

Pipeline собирается один раз на старте приложения, после инициализации BCI-провайдера и gRPC-клиента. Все источники регистрируются в маршрутизатор до того, как создаётся batcher (см. [docs/biometrics/capability-sources.md](capability-sources.md) про register-before-subscribe). Дальше pipeline молча работает фоном — UI его не дергает, и единственная внешняя точка управления — это lifecycle module-сессии.
