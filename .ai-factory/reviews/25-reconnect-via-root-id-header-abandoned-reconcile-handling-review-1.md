## Non-blocking observations

1. **[Low] Reconcile `Timer` is not cancelled on logout (`_reset`) or on the yield/terminal reset paths.** After `_resetWholeTree()` clears the registry (logout, `{abandoned}`, `rootDeath`, or SUPERSEDED yield), a settling-window `Timer` armed by the last `_openSessionStream` can still be pending and fires ~3s later. Its callback runs `removeById` on the already-cleared registry — harmless no-op removals — plus a `_notify()`. Functional impact is nil: `rootIdChanges` is `.distinct()` so the redundant `null→null` is absorbed before reaching `BiometricStreamClient._onRootIdChanged`, and nothing in `lib/` consumes the non-distinct `registryChanges`. A stale timer is also cancelled by the next `_openSessionStream` (`:145`) whenever a reopen happens within the window. Optional cleanup: cancel `_reconcileTimer` and null `_arrivedChildIds` inside `_resetWholeTree()` (or `_reset()`) for tidiness. Not required for correctness.

2. **[Info] Redundant reset in `takeOverHere()`.** `takeOverHere()` sets `_supersededOnThisStream = false` (`:326`) immediately before calling `_openSessionStream()`, which resets the same flag at its top (`:135`). Harmless duplication.

3. **[Info] Known API-gated limitation (documented in note 20 §40–41).** The 3s reconcile window will evict a genuinely-live concurrent second child if, on reconnect, the server sends a single collapsed RESUMED frame instead of a per-child RESUMED for each live child. This is the accepted design pending the mind_api per-child RESUMED follow-up (mind_api Phase 62); the client-side reconcile is correct given per-child RESUMED. Flagged for awareness, not a defect in this milestone.
